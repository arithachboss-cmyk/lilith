# ข้อตกลงการทำงานร่วมกัน — AMI screens

สองฝ่ายทำงานบนรีโปเดียวกันพร้อมกัน เอกสารนี้บอกว่าใครแตะอะไรได้
อะไรเป็นตัวตัดสินเวลาไม่ตรงกัน และต้องรันอะไรก่อน push

ตัวกลางคือรีโป ไม่ใช่การคุยกัน ทั้งสองฝ่ายอาจทำงานคนละเวลาและไม่เห็นกัน
ทุกอย่างในเอกสารนี้จึงต้องอ่านออกจากไฟล์ได้เอง

## ใครเป็นเจ้าของอะไร

| ไดเรกทอรี | เจ้าของ | อีกฝ่ายทำอะไรได้ |
|---|---|---|
| `hr-screens/` (ยกเว้น `codex/`) | prototype / spec | อ่านอย่างเดียว · เสนอแก้ผ่าน PR แยก ไม่แก้ในงานของตัวเอง |
| `hr-screens/codex/contract/*.json` | สัญญาร่วม | อ่านได้ · แก้ได้เฉพาะไฟล์ที่ไม่ได้ generate และต้องมีเหตุผลใน PR |
| `hr-screens/codex/contract/role-registry.json`, `screens.json` | **generate เท่านั้น** | **ห้ามแก้ด้วยมือ** แก้ที่ `hr-screens/data.js` แล้ว build ใหม่ |
| `apps/`, `packages/` | งาน implement (Codex) | ฝั่ง prototype ไม่แตะ |
| `docs/07-codex-handoff.md`, `docs/blueprint-source-manifest.json` | Blueprint | **ไม่มีใครแก้** ADR-0013 กำหนดให้นำเข้าโดยไม่แก้เนื้อหา |
| `pnpm-lock.yaml` | workspace | แก้ได้เฉพาะเมื่อเพิ่ม dependency จริง และต้องอยู่ใน PR ที่อธิบายไว้ |

AGENTS.md ระบุอยู่แล้วว่า *"Creating additional files is fine; touching files owned
by another in-flight task is not"* — ตารางข้างบนคือการระบุว่า in-flight task
ของ AMI ครอบไฟล์ไหนบ้าง

## ตัวตัดสิน

```bash
node hr-screens/codex/check-contract.mjs
```

รันก่อน push ทุกครั้งที่แตะอะไรใน `hr-screens/` หรือใน contract
ตอนนี้ตรวจ 218 ข้อ และ exit ไม่เป็นศูนย์เมื่อพัง จุดที่สำคัญที่สุดสามข้อ

1. **ค่าต้องตรงกับตารางในบรีฟ** checker ฝังตารางไว้ในตัวเอง ไม่ได้อ่านจาก `data.js`
   ถ้าอ่านจากแหล่งเดียวกับที่ตรวจ การตรวจก็ไม่ได้ตรวจอะไรเลย
2. **ไฟล์ที่ generate ต้องไม่หลุดจาก `data.js`** ถ้าแก้มือ มันฟ้องทันที
3. **ข้อความต้องมีครบสองภาษา** ตาม definition of done ของรีโป

ถ้า checker ฟ้อง ให้แก้ที่ต้นเหตุ **ห้ามแก้ checker ให้ผ่าน** เว้นแต่ checker เองผิด
ซึ่งกรณีนั้นต้องอธิบายใน PR ว่าผิดตรงไหนและทำไม

## เวลาสัญญาไม่พอใช้

implementation จะเจอเรื่องที่สัญญาไม่ได้ครอบ นี่เป็นเรื่องปกติ ไม่ใช่ความผิดพลาด

- **ต้องเพิ่มช่องหรือ enum** → เสนอใน PR ของงานนั้น พร้อมบอกว่าจะใช้ที่ไหน
  ฝั่ง spec แก้ `data.js` หรือไฟล์สัญญาแล้ว build ใหม่ ไม่ใช่ให้ implementation
  แก้ไฟล์ generate เอง
- **สัญญาขัดกับความจริงของระบบ** → หยุดแล้วรายงาน อย่าเงียบ ๆ ออกแบบใหม่
  (AGENTS.md ข้อ 5 ของ §30.0)
- **สัญญาถูก แต่ทำตามไม่ได้ในเฟสนี้** → เขียนไว้ใน BLOCKERS ของ PR ไม่ใช่ลดสัญญาลง

## ลำดับงานและสิ่งที่ติดอยู่

การ์ดงานอยู่ใน `TASKS.md` เจ็ดใบ รูปแบบเดียวกับ §30

- **เริ่มได้ทันที ไม่ติดอะไร** — `AMI-001` (role registry + contract package)
- **ทำคู่ขนานได้** — `AMI-002` (สตริงสองภาษา)
- **ติดคำตัดสินของเจ้าของระบบ** — `AMI-003` ถึง `AMI-007`

สี่เรื่องที่ต้องตัดสินก่อน `AMI-003` อยู่ท้าย `TASKS.md` เรื่องที่หนักที่สุดคือ
**วิธีเข้าสู่ระบบ** ซึ่งบรีฟกับ `docs/03-security-events-admin.md` ขัดกันตรง ๆ
(อีเมล + รหัสเริ่มต้น เทียบกับ No passwords in V1 ที่ใช้ OTP)
อย่าเดาข้างใดข้างหนึ่งแล้วเขียนต่อ

## กติกาที่ใช้ร่วมกัน

- หนึ่งงาน หนึ่ง branch หนึ่ง PR ตาม §30.0
- งานเสร็จเมื่อเกณฑ์รับงานเป็นจริงและพิสูจน์ได้ใน CI ไม่ใช่แค่เขียนเสร็จ
- ห้ามลดทอน constraint, authz check หรือเทสต์ เพื่อให้ผ่าน
- ปิด PR ด้วย `STATUS / EVIDENCE / RISKS / BLOCKERS / NEXT / OWNER APPROVAL`
- `pnpm build`, `typecheck`, `lint`, `test:boundaries` ต้องผ่านก่อน push
- ตัวสลับ "ดูตัวอย่างบทบาท" ของ prototype **ต้องไม่มีในของจริง**
