# นับสต็อกด้วยบาร์โค้ด — ตัวเลขบอกอะไรและไม่บอกอะไร

การนับด้วยบาร์โค้ดทำให้ได้ยอดคงเหลือเร็วกว่าและเหนื่อยน้อยกว่าการนับด้วยมือ นั่นเป็นเรื่องจริงและเป็นเหตุผลที่ดีพอสำหรับการเริ่ม

แต่มีความเข้าใจผิดที่ทำให้หลายที่ผิดหวังตามมา — **การนับไม่ได้แก้ส่วนต่าง มันแค่ทำให้เห็นส่วนต่างเร็วขึ้น** ถ้าต้นทางยังผิดอยู่ การนับถี่ขึ้นก็เพียงทำให้เห็นปัญหาเดิมบ่อยขึ้น

## การนับหนึ่งครั้งตอบคำถามเดียว

ผลการนับบอกว่า **ณ เวลาที่นับ ตรงนั้นมีจำนวนเท่าไร** เท่านั้น

สิ่งที่มันไม่ได้บอก

- ของหายไปตั้งแต่เมื่อไร
- หายระหว่างขั้นตอนไหน
- เป็นการหายจริง หรือเป็นการบันทึกที่ไม่ตรง
- ของอยู่ผิดที่ หรือไม่อยู่ในคลังแล้ว

คำถามทั้งสี่ข้อนี้ตอบได้จาก **ร่องรอยระหว่างทาง** ไม่ใช่จากผลการนับ ซึ่งแปลว่าถ้าไม่ได้บันทึกระหว่างทาง การนับจะบอกได้แค่ว่ามีปัญหา แต่บอกไม่ได้ว่าปัญหาอยู่ตรงไหน

## ส่วนต่างมาจากไหนได้บ้าง

| ต้นเหตุ | เกิดตรงไหน | อาการที่เห็น |
|---|---|---|
| รับเข้าไม่ตรงกับที่บันทึก | จุดรับ | ส่วนต่างเกิดกับสินค้ากลุ่มเดียวกันซ้ำ ๆ จากผู้ส่งรายเดิม |
| หยิบผิดชิ้นแต่บันทึกถูก | จุดหยิบ | ยอดของสองรายการสลับกัน ตัวหนึ่งเกิน อีกตัวขาด |
| ย้ายของโดยไม่บันทึก | ภายในคลัง | นับได้ครบแต่ระบบบอกว่าอยู่คนละที่ |
| บันทึกสองครั้งจากเหตุการณ์เดียว | ทุกจุด | ยอดในระบบมากกว่าที่นับได้ |
| ของเสียหายหรือคืนโดยไม่ผ่านขั้นตอน | ปลายทาง | ส่วนต่างโผล่เป็นครั้งคราวโดยไม่มีรูปแบบ |

<!-- claim: CLM-S-004 -->
สามข้อแรกแยกแยะได้ก็ต่อเมื่อมีรหัสที่ไม่ซ้ำกันและมีการบันทึกที่จุดเกิดเหตุ ซึ่งการกำหนดรหัสสินค้าที่ไม่ซ้ำกันเป็นพื้นฐานของการตรวจสอบย้อนกลับอยู่แล้ว การนับจึงให้ประโยชน์เต็มที่เมื่อต่อกับข้อมูลระหว่างทาง ไม่ใช่เมื่อนับบ่อยขึ้นอย่างเดียว

## นับทั้งคลังทีเดียว หรือนับทีละส่วนตามรอบ

<!-- claim: CLM-S-006 -->
เกณฑ์การเลือกควรมาจากเงื่อนไขการใช้งานจริง ไม่ใช่จากความเคยชิน

| | นับทั้งคลังทีเดียว | นับทีละส่วนตามรอบ |
|---|---|---|
| ได้ภาพรวมตรงกันทั้งคลัง | ได้ | ไม่ได้ในทีเดียว |
| ต้องหยุดงานหรือไม่ | มักต้องหยุด | ทำระหว่างงานปกติได้ |
| พบส่วนต่างเร็วแค่ไหน | รู้ตอนถึงรอบ | รู้เร็วกว่าในกลุ่มที่นับถี่ |
| ใช้กับอะไร | ปิดบัญชี หรือเริ่มต้นระบบใหม่ | การดูแลระหว่างปี |
| จุดอ่อน | ระหว่างรอบไม่มีข้อมูล | ต้องออกแบบว่าอะไรนับถี่ อะไรนับห่าง |

**สองแบบนี้ไม่ได้แทนกัน** ที่หลายที่ใช้คือนับทั้งคลังตอนเริ่มระบบเพื่อตั้งจุดตั้งต้นให้ตรง แล้วดูแลด้วยการนับตามรอบหลังจากนั้น

การเลือกว่ากลุ่มไหนควรนับถี่ ควรมาจากผลที่เกิดเมื่อยอดไม่ตรง ไม่ใช่จากจำนวนชิ้น — ของที่ขาดแล้วงานหยุด กับของที่ขาดแล้วรอได้ ไม่ควรอยู่ในรอบเดียวกัน

## สิ่งที่ต้องตกลงก่อนเริ่มนับ

- **ขอบเขตของการนับ** — นับทั้งหมด หรือเฉพาะบางกลุ่ม และของที่อยู่ระหว่างขนย้ายนับหรือไม่
- **จะหยุดการเคลื่อนไหวระหว่างนับไหม** — ถ้าไม่หยุด ต้องมีวิธีแยกของที่เคลื่อนระหว่างนับออกจากส่วนต่างจริง
- **ใครยืนยันผล** — คนที่นับกับคนที่อนุมัติการปรับยอดควรเป็นคนละคน
- **ปรับยอดแล้วเหลือร่องรอยไหม** — ถ้าปรับได้โดยไม่ทิ้งร่องรอย ตัวเลขจะค่อย ๆ เชื่อถือไม่ได้โดยไม่มีใครสังเกต
- **นับซ้ำเมื่อไร** — ส่วนต่างที่เกินเกณฑ์ที่ตกลงไว้ ควรนับซ้ำก่อนปรับ ไม่ใช่ปรับทันที

ข้อสุดท้ายป้องกันปัญหาที่พบบ่อย — การปรับยอดตามผลนับครั้งเดียวทำให้ความผิดพลาดของการนับกลายเป็นข้อมูลจริงในระบบ

## ทดสอบกระบวนการ ไม่ใช่แค่อุปกรณ์

<!-- claim: CLM-S-005 -->
ควรทดสอบในสภาพแวดล้อมจริงก่อนนำไปใช้งานเต็มรูปแบบ และสำหรับการนับ สิ่งที่ต้องทดสอบคือกระบวนการ ไม่ใช่แค่ว่าเครื่องอ่านฉลากออกหรือไม่

<!-- claim: CLM-S-001 -->
การใช้บาร์โค้ดแทนการคีย์ข้อมูลด้วยมือช่วยลดโอกาสเกิดความผิดพลาดจากการพิมพ์ แต่การนับยังมีทางผิดพลาดอีกหลายทางที่ไม่เกี่ยวกับการพิมพ์

| ต้องลอง | ดูอะไร |
|---|---|
| นับพื้นที่เดียวกันสองครั้งโดยคนละคน | ได้ผลตรงกันหรือไม่ · ถ้าไม่ตรง แปลว่ากระบวนการยังไม่นิ่ง |
| ของที่ฉลากอ่านไม่ผ่าน | มีทางบันทึกหรือผู้ใช้ข้ามไปเฉย ๆ |
| ของที่อยู่ผิดตำแหน่ง | ระบบบันทึกว่าเจอที่ไหน หรือบันทึกแค่ว่าเจอ |
| นับระหว่างที่ยังมีการเคลื่อนไหว | แยกของที่เคลื่อนออกจากส่วนต่างจริงได้ไหม |
| ของที่ไม่มีในระบบเลย | มีทางเดินให้หรือผู้ใช้ต้องหาทางลัด |

**ข้อแรกคือข้อที่ให้คำตอบชัดกว่าข้ออื่น** ถ้าคนสองคนนับพื้นที่เดียวกันแล้วได้ไม่ตรงกัน ปัญหาอยู่ที่กระบวนการหรือการจัดวาง ไม่ใช่ที่ระบบ และการเพิ่มอุปกรณ์จะไม่แก้

## สรุป

บาร์โค้ดทำให้การนับเร็วขึ้นและทำได้บ่อยขึ้น ซึ่งมีค่าจริง แต่คุณค่าที่แท้จริงเกิดเมื่อผลการนับ **ต่อกับร่องรอยระหว่างทาง** จนตอบได้ว่าส่วนต่างมาจากขั้นตอนไหน

การนับที่ไม่ต่อกับอะไรเลย ให้ผลลัพธ์เดียวคือรู้ว่ามีปัญหา — ซึ่งดีกว่าไม่รู้ แต่ยังไม่พอสำหรับการแก้
