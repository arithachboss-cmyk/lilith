# Deal state machine

The full graph lives in `src/domain/deals/state-machine.ts`; `canTransition` is pure. `transitionDeal` in `src/services/platform/deals.ts` authorizes and persists implemented commands with compare-and-swap, audit and events.

```text
MATCH_CREATED → INTEREST_EXPRESSED → MUTUAL_MATCH → DEAL_ROOM_OPENED
 → VIEWING_REQUESTED → VIEWING_CONFIRMED → VIEWING_COMPLETED
 → OFFER_SUBMITTED → COUNTER_OFFER / NEGOTIATION / AGREEMENT_PENDING
 → AGREEMENT_SIGNED → DEAL_CLOSED
```

Any nonterminal state can reach CANCELLED where allowed by the graph; CANCELLED and DEAL_CLOSED have no outgoing transitions. Negotiation/counteroffer loops are explicitly represented in code.

Before a room exists, Match owns the consent state. Mutual interest opens the room atomically, whose initial state is DEAL_ROOM_OPENED. Clients cannot assign a status directly.

Delivered APIs allow request viewing, confirm viewing, complete viewing, or cancel. The requester cannot confirm their own viewing. Confirmation requires a future appointment; completion requires its scheduled time to have elapsed. Either participant can request or record completion. Appointment dates are stored as ISO UTC; the UI displays local time. Requests must be within the next year. This is recorded as an implementation scheduling limit, not a fee/negotiation rule.

The update checks current state and version. Child viewing rows, audit and events are inserted only if the operation ID matches the successful update. Lost races return `STALE_DEAL` with 409. Request retries return the same viewing; actor/key reuse with different room/time/notes returns `IDEMPOTENCY_CONFLICT`.

Offer, negotiation, agreement signatures and closing are modeled but have no executable workflow yet. The generic transition endpoint deliberately rejects these targets. No fee can be generated by pretending a deal has closed.
